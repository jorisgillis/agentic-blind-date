# Agentic Blind Date - Domain Context

This document captures the **ubiquitous language** and **key concepts** for the Agentic Blind Date project.

## Core Domain

### Event
A single meetup session where participants are matched using AI agents. Currently, the application supports a single continuous event, with future plans for multiple events with data carry-over between sessions.

### Participant
A person attending the meetup event. Each participant goes through the onboarding pipeline to create their profile and persona.

### Persona
A fun, anonymous identity generated for a participant. Consists of:
- **Name**: A tongue-in-cheek title (e.g., "The Pragmatic Go Guru")
- **Tagline**: A short, humorous description
- **Color**: A Tailwind CSS background color for visual identification
- **Symbol**: An emoji for visual identification

The persona allows participants to be identifiable in the room without revealing their real identity.

### Pipeline
The automated process that each participant goes through:
1. **Fetching GitHub**: Retrieve and parse GitHub profile data
2. **Interviewing**: Participant answers questions (fixed + custom)
3. **Generating Persona**: LLM creates the fun persona based on profile and answers
4. **Ready**: Participant is ready for matching

### Pipeline Step
The current stage of a participant in the pipeline. Valid values:
- `fetching_github`
- `interviewing`
- `generating_persona`
- `ready`

Note: `creating_persona` is an alias for `generating_persona` used in some templates.

### Match
A pairing between two participants based on compatibility. Contains:
- **Compatibility Score**: 0-100 numeric score
- **Reason**: A funny one-liner explaining the match
- **Green Flags**: Positive aspects of the match
- **Red Flags**: Potential concerns (presented humorously)
- **Icebreakers**: Conversation starter questions

### Compatibility Score
A numeric score from 0-100 indicating how well two participants match. Generated by:
1. **Heuristic Score**: Fast, cheap score using profile attributes (languages, topics, etc.)
2. **LLM Score**: Score generated by Mistral LLM based on full profile comparison

### Heuristic Score
A fast, deterministic score used to filter candidate pairs before expensive LLM scoring. Computed by `pairScore()` function using:
- Shared languages: +3 per match
- Shared interview answers: +1 per match
- Shared GitHub topics: +2 per match
- Shared project types: +2 if same
- GitHub follow relationships: +5 if mutual, +3 if one-way
- Shared dev environments: +1 per match

### LLM Score
A compatibility score generated by the Mistral LLM. The LLM receives:
- Both participants' GitHub profile summaries
- Both participants' interview answers
- Both participants' interests (languages, tools, domains)
- GitHub follow relationship status

The LLM returns a JSON response with score, reason, flags, and icebreakers.

### Continuous Matching
The process of automatically matching participants as they become ready. Unlike batch matching, continuous matching:
- Runs as each participant reaches `ready` state
- Can break existing matches if a better candidate arrives
- Maintains a dynamic pool of ready participants

### Matching Algorithm
The 3-phase algorithm for pairing participants:
1. **Heuristic Filtering**: For each participant, find top-5 candidates using `pairScore`
2. **LLM Scoring**: Score each candidate pair using Mistral LLM
3. **Greedy Assignment**: Sort by score and assign highest first

### Candidate Pair
A potential match between two participants that has passed the heuristic filter but not yet been scored by LLM.

### Graph
The network visualization shown on the big screen, consisting of:
- **Nodes**: Participants represented as colored circles with emoji symbols
- **Edges**: Connections between participants
  - Matched edges: Actual matches (solid lines)
  - Potential edges: Top-3 heuristic connections (dashed lines)

### Big Screen
The public display for the event, showing:
- All participants as a graph
- Match announcements
- Activity ticker
- Event statistics

### Interview
The question-and-answer process where participants provide information about themselves. Consists of:
- **Fixed Questions**: Standard questions all participants answer
- **Custom Questions**: LLM-generated questions tailored to GitHub profile (GitHub users only)
- **Extra Questions**: Manual questions for non-GitHub users

### Fixed Questions
Standard questions that all participants answer:
- Tabs or spaces?
- What's your go-to language right now?
- Would you deploy on a Friday?
- Monolith or microservices?
- Your git commit style?
- Which AI coding assistant do you prefer?

### Custom Questions
Questions generated by LLM based on a participant's GitHub profile. Intended to be personalized and relevant to their specific background.

### Extra Questions
Manual questions for participants without GitHub accounts:
- What are your top 3 programming languages?
- What type of projects do you most enjoy working on?
- What's your preferred development environment?
- What's the weirdest bug you've ever fixed?
- Keyboard preference?

### GitHub Profile
Data fetched from a participant's GitHub account, including:
- Basic info: login, name, bio, company, location
- Statistics: public repos, followers, account age, total stars
- Languages: extracted from repository languages
- Top Topics: extracted from repository topics
- Top Repos: up to 5 most-starred repositories
- Has Profile README: whether user has a profile README

### Interests
Computed attributes that categorize a participant's technical profile:
- **Languages**: Programming languages used
- **Tools**: Tools and technologies (from GitHub topics or manual input)
- **Domains**: Areas of work (e.g., Web Development, Backend Services)

### Follow Relationship
Social connection between participants on GitHub:
- **Mutual Follow**: Both participants follow each other
- **One-way Follow**: One participant follows the other
- **No Follow**: No follow relationship

### Event State
Global state of the application:
- Currently always `matching` (simplified from previous onboarding/matching/revealed)

### Relationship State
The matching status of a participant:
- **Unmatched**: Not currently matched with anyone
- **Matched**: Currently matched with another participant

Note: Relationship state is independent of pipeline state. A participant can be `ready` (pipeline) and `matched` or `unmatched` (relationship).

## Subdomains

### Onboarding Subdomain
Responsible for participant entry into the system. Includes:
- Landing page
- GitHub profile fetching
- Profile parsing
- Persona generation
- Question generation

### Matching Subdomain
Responsible for pairing participants. Includes:
- Heuristic scoring
- LLM scoring
- Greedy assignment
- Continuous matching
- Cache management

### Visualization Subdomain
Responsible for displaying event data. Includes:
- Big screen graph
- Participant cards
- Match announcements
- Activity ticker

### Administration Subdomain
Responsible for event management. Includes:
- Event reset
- Rematching
- Monitoring
- Configuration

## Key Invariant

A participant can only be matched with one other participant at a time. When a new match is formed, any existing match for either participant is broken.

## Glossary

| Term | Definition |
|------|------------|
| Agent | An AI-powered component that performs a specific task (e.g., persona generation, matching) |
| Handle | GitHub username |
| Profile | Collection of data about a participant (GitHub data + answers) |
| Summary | Textual representation of a profile for LLM consumption |
| Score | Numeric compatibility rating (0-100) |
| Pair | Two participants being evaluated for matching |
| Pool | Collection of ready, unmatched participants available for matching |
