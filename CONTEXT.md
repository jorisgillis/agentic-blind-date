# Agentic Blind Date - Domain Context

This document captures the **ubiquitous language** and **key concepts** for the Agentic Blind Date project.

## Core Domain

### Event
A single meetup session where participants are matched using AI agents. Currently, the application supports a single continuous event, with future plans for multiple events with data carry-over between sessions.

### Participant
A person attending the meetup event. Each participant goes through the onboarding pipeline to create their profile and persona.

### Persona
A fun, anonymous identity generated for a participant. Consists of:
- **Name**: A tongue-in-cheek title (e.g., "The Pragmatic Go Guru")
- **Tagline**: A short, humorous description
- **Color**: A Tailwind CSS background color for visual identification
- **Symbol**: An emoji for visual identification

The persona allows participants to be identifiable in the room without revealing their real identity.

The **Persona module** is the only place a Persona is made. When the LLM fails it falls back to an anonymous Persona named after the Participant's main language ("The Go Developer"), never after their handle or name.

### Pipeline
The automated process that each participant goes through:
1. **Fetching GitHub**: Retrieve and parse GitHub profile data and prepare the question set. The Interview only starts (`interviewing`) once the question set is stored
2. **Interviewing**: Participant answers questions (fixed + custom)
3. **Generating Persona**: LLM creates the fun persona based on profile and answers
4. **Ready**: Participant is ready for matching

The **Onboarding module** runs the pipeline: registration, preparing the Interview, and, once every question is answered, creating the Persona, computing Interests, making the Participant ready and handing them to Continuous Matching.

### Pipeline Step
The current stage of a participant in the pipeline. Steps only move forward, one at a time (only an event Reset starts over), so each step is entered at most once. Valid values:
- `fetching_github`
- `interviewing`
- `creating_persona`
- `ready`

### Match
A pairing between two participants based on compatibility. Contains:
- **Compatibility Score**: 0-100 numeric score
- **Reason**: A funny one-liner explaining the match
- **Green Flags**: Positive aspects of the match
- **Red Flags**: Potential concerns (presented humorously)
- **Icebreakers**: Conversation starter questions

### Teaser
What a matched Participant sees on the wait page during onboarding: their future Match's **emoji and colour** and a hint at the first question the pair answered differently ("You disagreed on the Friday-deploy question — reveal at the break"). The Teaser is the curiosity gap before the Reveal: it carries no identity, score, reason, flags or icebreakers.

### Dossier
The Match's fun payload — the **reason**, the **red/green flags** and the **icebreakers** — shown on the Match page as locked cards (playful blurred placeholders, the payload itself never in the page) until the pair's dossier unlocks. The dossier unlocks once the pair's Meeting is **completed** (or the event is closed, after which the recap takes over) and arrives by push, without a manual refresh. The compatibility score is not part of the dossier: it is revealed with the Match itself.

### Compatibility Score
A numeric score from 0-100 indicating how well two participants match. Generated by:
1. **Heuristic Score**: Fast, cheap score using profile attributes (languages, topics, etc.)
2. **LLM Score**: Score generated by Mistral LLM based on full profile comparison

### Heuristic Score
A fast, deterministic score used to filter candidate pairs before expensive LLM scoring. Computed by the Matcher's `PairScore` method using:
- Shared languages: +3 per match
- Shared interview answers: +1 per match
- Shared GitHub topics: +2 per match
- Shared project types: +2 if same
- GitHub follow relationships: +5 if mutual, +3 if one-way
- Shared dev environments: +1 per match

### LLM Score
A compatibility score generated by the Mistral LLM. The LLM receives:
- Both participants' GitHub profile summaries
- Both participants' interview answers
- Both participants' interests (languages, tools, domains)
- GitHub follow relationship status

The LLM returns a JSON response with score, reason, flags, and icebreakers.

### Continuous Matching
The process of automatically matching participants as they become ready. Unlike batch matching, continuous matching:
- Runs as each participant reaches `ready` state, i.e. once they have completed every pipeline step (Interview answered, Persona created), in any event phase including onboarding
- During onboarding, can break existing matches if a better candidate arrives; the partner left behind is matched again straight away, but never with the pair that just displaced them
- Freezes at the social: from `social` onward pairs are final — a latecomer is paired only with other *unmatched* ready participants, never displacing a matched one, and the admin's Rematch is disabled
- Maintains a dynamic pool of ready participants

The **Matchmaking module** runs matching operations one at a time: the admin's Rematch and Continuous Matching for a newcomer. The Matcher decides who fits; the Relationship module records it.

### Matching Algorithm
The 3-phase algorithm for pairing participants:
1. **Heuristic Filtering**: For each participant, find top-5 candidates using `PairScore`
2. **LLM Scoring**: Score each candidate pair using Mistral LLM
3. **Greedy Assignment**: Sort by score and assign highest first

### Candidate Pair
A potential match between two participants that has passed the heuristic filter but not yet been scored by LLM.

### Graph
The network visualization shown on the big screen, consisting of:
- **Nodes**: Participants represented as colored circles with emoji symbols
- **Edges**: Connections between participants
  - Matched edges: Actual matches (solid lines)
  - Potential edges: Top-3 heuristic connections (dashed lines)

### Theme
A named look for the application: colours, typography, shape, motion and sound. Each Participant chooses a Theme for their own phone, and the choice stays with that device. The admin chooses the Theme of the Big Screen. Persona colours are the same in every Theme, because they identify Participants in the room.

### Event Format
How the event runs, chosen by the admin before the event starts:
- **Classic flow**: each Participant goes through the Interview on their own phone, and Continuous Matching pairs them as they become ready.
- **Game Show**: the Big Screen is the stage and phones are controllers. A Host runs the show in Rounds, and everyone is paired at once in the matchmaking segment.

Both formats share registration, Personas, matching, Themes and the Reveal.

### Host
The admin running a Game Show from the host console: starting the show, opening and closing Rounds, starting the matchmaking segment, and the Reveal.

### Show Segment
A stage of a Game Show, in order: the **Lobby** (Participants answer their personalised questions on their own), the Rounds, the matchmaking segment (everyone ready is paired at once), the Reveal (pair by pair), and the **Afterparty** (arrivals after the Reveal are matched by Continuous Matching).

### Round
In a Game Show, one Fixed Question answered by every Participant at the same moment on their phone, with a countdown, while the Big Screen shows the room's answers live.

### Big Screen
The public display for the event, showing:
- All participants as a graph
- Match announcements
- Activity ticker
- Event statistics

### Interview
The question-and-answer process where participants provide information about themselves. Consists of:
- **Fixed Questions**: Standard questions all participants answer
- **Custom Questions**: LLM-generated questions tailored to GitHub profile (GitHub users only)
- **Extra Questions**: Manual questions for non-GitHub users

The **Interview module** owns a Participant's progress through the Interview: the next unanswered question, validating and recording answers (including multi-select), and signalling completion.

### Fixed Questions
Standard questions that all participants answer:
- Tabs or spaces?
- What's your go-to language right now?
- Would you deploy on a Friday?
- Monolith or microservices?
- Your git commit style?
- Which AI coding assistant do you prefer?

### Custom Questions
Questions generated by LLM based on a participant's GitHub profile. Intended to be personalized and relevant to their specific background.

### Extra Questions
Manual questions for participants without GitHub accounts:
- What are your top 3 programming languages?
- What type of projects do you most enjoy working on?
- What's your preferred development environment?
- What's the weirdest bug you've ever fixed?
- Keyboard preference?

### GitHub Profile
Data fetched from a participant's GitHub account, including:
- Basic info: login, name, bio, company, location
- Statistics: public repos, followers, account age, total stars
- Languages: extracted from repository languages
- Top Topics: extracted from repository topics
- Top Repos: up to 5 most-starred repositories
- Has Profile README: whether user has a profile README

### Non-GitHub User
A participant who registers without a GitHub account. These users go through a modified onboarding flow:
- **Handle**: Automatically generated as `"no-github-{uuid-prefix}"` to ensure uniqueness. It is only a unique key: whether a Participant has a GitHub account is recorded at registration, never inferred from the handle
- **Pipeline**: Skips the GitHub fetch; moves to `interviewing` as soon as their question set is stored
- **Questions**: Answers ExtraQuestions instead of FixedQuestions + CustomQuestions
- **Profile Data**: When the Interview completes, the answers to the Extra Questions are turned into **ExtraAnswers** (languages, project type, dev environment, weirdest bug, keyboard) on their profile. This also happens for GitHub users who got the Extra Questions as a fallback

### Interests
Computed attributes that categorize a participant's technical profile. GitHub data is preferred; ExtraAnswers fill the gaps:
- **Languages**: Programming languages used
- **Tools**: Tools and technologies (from GitHub topics or manual input)
- **Domains**: Areas of work (e.g., Web Development, Backend Services)

### Follow Relationship
Social connection between participants on GitHub:
- **Mutual Follow**: Both participants follow each other
- **One-way Follow**: One participant follows the other
- **No Follow**: No follow relationship

### Event State
Global state of the event — its **Phase** — changed only by the host from the host console. Phases only move forward: the host may jump ahead (e.g. `social` → `closed` for a short evening), advancing to the current phase is a no-op, and backward transitions are rejected.
- **Onboarding** (`onboarding`): the default after a Reset. Participants register and Continuous Matching runs, but Matches stay hidden. Matched Participants wait on the wait page and see a teaser, and the Big Screen shows persona names only.
- **Social** (`social`): the Big Reveal at the break. Matches are revealed and every Match page opens — the full persona card, no handles — while the Dossier stays locked; newcomers see their Match as soon as they are matched. Matching freezes: pairs are final. Mission cards go live and meeting confirmation opens.
- **Show & Tell** (`showtell`): everything in the Social stays; show & tell sign-up and the question queue go live, and the Big Screen gains presenter mode.
- **Closed** (`closed`): meeting confirmation is disabled; the closing view shows a recap QR, and personal recap pages persist. The dossiers unlock: the assessment is visible again, on the page and in the JSON debug endpoints.

Rematching does not change the Phase; Reset returns it to `onboarding`. A database holding the legacy value `revealed` is migrated to `social` at startup. The Big Screen shows persona names only, in every phase.

### Relationship State
The matching status of a participant:
- **Unmatched**: Not currently matched with anyone
- **Matched**: Currently matched with another participant

Note: Relationship state is independent of pipeline state. A participant can be `ready` (pipeline) and `matched` or `unmatched` (relationship).

### Meet Code
A 6-character code a participant shows (as text or QR) so someone else can confirm meeting them. Drawn from an unambiguous alphabet (no `0/O/1/I`), derived deterministically from the participant's id, unique; a collision re-derives deterministically with a salt. Assigned at registration; existing participants are backfilled at startup.

### Meet Link
`{base}/user/m/{id}` — the participant's meet page, rendered as a QR on their personal page. Opening it shows the target's persona card and a confirm button.

### Meeting
A confirmed physical meeting between two participants. Stored as one canonical row per pair (`participant_a` = lexicographically lower id), with each side's confirmation tracked separately (`a_confirmed_at` / `b_confirmed_at`) and `completed_at` set when both sides have confirmed. Confirmation is a two-sided handshake, open only during the Social and Show & Tell phases; a one-sided confirmation is pending and expires silently on Reset. The meeting's **Origin** (`match` / `mission` / `other`) is tagged automatically at creation from the initiator's perspective (match is symmetric; mission is not). Meeting anyone counts, not only mission tiles.

### Connection
A participant's count of completed meetings — one connection per completed meeting. Derived from the meetings table, never stored.

### Champion
The Merge Trophy winner: the participant with the most completed meetings — the top of the connection leaderboard. Deterministic: most connections, ties broken by persona name. The champion is named on the ticker when the event closes; the closing ceremony screen itself is a later ticket.

### Mission Card
A participant's personal 3×3 grid of personas to meet, live during the Social and Show & Tell. Cards are generated at the social transition for everyone ready — in a background worker pool, so the transition returns immediately — and straight away for latecomers reaching ready during those phases; never during onboarding or once closed. The center tile is the participant's Match, falling back to their top-affinity persona while unmatched; the eight surrounding tiles are four affinity picks (highest heuristic pair score) and four wildcards (deliberately different), excluding the Match, the participant, and everyone already met. Tiles snapshot the persona at generation, so a card is fixed once dealt. A **Stamp** marks a tile whose person the participant has a completed Meeting with — stamps derive from the meetings, never stored. The surrounding tiles' reasons come from the **Mission Agent**: one batched LLM call per card, with a generic fallback reason when the LLM fails, so a card always generates. Card generation never writes pairing data.

### Contact Channel
A contact detail a Participant can share with the people they met: github, email, linkedin, instagram, mastodon or other. Channels are entered once in the settings section of the personal page, off by default; the github channel is pre-filled from the Participant's GitHub profile. A channel's value leaves its owner's hands only under the **mutual rule** (`Revealed`, in `contact.go`): a channel is revealed to the other side only if the owner opted in to it AND the pair's Meeting is completed — a one-sided opt-in reveals nothing. After a completed meeting, both phones show an "Exchange contact details?" prompt with what each side shares. The `/data` debug endpoints show per-Participant opted-in channel counts only, never values.

### Personal Recap
A Participant's page of their evening, kept: `GET /user/recap/{token}`, gated by an unguessable UUID token stored in the `recaps` table, so the page persists across restarts. The recap shows the Participant's persona card, their match dossier (always unlocked there), every connection with the contact channels those connections shared, the channels the Participant shared themselves, and their personal stats (connections, leaderboard rank, champion). During `closed`, the personal page shows the recap link as a QR. A GitHub handle appears on the owner's own recap only as a revealed github contact channel — the owner opted in — and nowhere else outside stage.

### Show & Tell
The stage of the `showtell` phase: Participants volunteer a talk, the Host runs the queue, the Big Screen presents the current speaker. A **Sign-up** is one row per Participant in `showtell_signups` — a title (required), a one-line description, an optional repo link — live during the Social and Show & Tell phases only; late sign-ups join the tail of the queue, and re-signing up updates the talk in place. A sign-up's **Status** is `queued` → `on_stage` → `presented`. The Host's queue (in `/admin`) reorders queued talks up/down and removes any of them. **Presenter mode** is a show & tell gain: the Host puts one queued sign-up on stage — the Big Screen shows their persona card with the **Hype Agent's** intro line (a generic fallback when the LLM fails) — and marks the talk done to free the stage. The **Identity Reveal** is the Host's explicit action and the only one: it flips the presenter's card to their GitHub handle/name. Personas only, everywhere, otherwise; the reveal is the single place a handle reaches the Big Screen besides the owner's own recap. Everything arrives by push — the personal pages' streams watch the Participant's sign-up state, the host console's queue stream watches the queue, the Big Screen's stream pushes the presenter card and the reveal.

## Subdomains

### Onboarding Subdomain
Responsible for participant entry into the system. Includes:
- Landing page
- GitHub profile fetching
- Profile parsing
- Persona generation
- Question generation

### Matching Subdomain
Responsible for pairing participants. Includes:
- Heuristic scoring
- LLM scoring
- Greedy assignment
- Continuous matching
- Cache management

### Visualization Subdomain
Responsible for displaying event data. Includes:
- Big screen graph
- Participant cards
- Match announcements
- Activity ticker

### Administration Subdomain
Responsible for event management. Includes:
- Event reset
- Rematching
- Monitoring
- Configuration

## Key Invariant

A participant can only be matched with one other participant at a time. When a new match is formed, any existing match for either participant is broken.

The **Relationship module** owns Relationship State and enforces the Key Invariant: every change to who is matched with whom (pairing, taking over a Match, unpairing) goes through it as one transaction. A partner left behind by a take-over is returned to the Pool.
